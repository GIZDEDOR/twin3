# Шаблон кейсов Twin3D

Изменения подготовлены локально. GitHub, сервер и удалённые модели Prismic автоматически не меняются.

## Посмотреть до заполнения админки

Из папки проекта запустите `npm run dev -- --port 3100`.

Откройте http://localhost:3100/projects/preview-yota. Это пример на материалах Yota из ТЗ и существующей карточки. Он работает только при `npm run dev`, имеет `noindex`, отсутствует в sitemap и не создаёт документ в Prismic. В рабочей сборке адрес возвращает 404. В локальном каталоге нажмите «Показать кейс» на карточке Yota: откроется `/projects/yota`. Пока документ Yota не опубликован в Prismic, только в режиме разработки используются демонстрационные данные. Отдельная ссылка над каталогом удалена.

## Как добавить поля в Prismic

1. Запустите `npm run slicemachine` из этой же папки.
2. Откройте http://localhost:9999 и войдите в Prismic, если потребуется. Репозиторий: `twin3`.
3. В разделе **Custom types** проверьте новый повторяемый тип **Кейс** (`project`), а в **Slices → CaseFilters** дополнительное поле **Страница кейса**.
4. После проверки нажмите **Review changes** и отправьте эти модели через **Push changes**. Это отдельное действие: обычный Git-коммит не добавляет поля в Prismic. Push изменяет схему настоящей админки, но не публикует кейсы.
5. Перезагрузите Prismic. Создайте документ типа **Кейс**.

Существующий тип **Projects** и его карточки сохраняются. Не удаляйте его и не переносите всю ленту. Старый `components/CaseFilters.tsx` не изменён: используется `slices/CaseFilters/index.tsx`.

## Что заполнять

Вкладка **Основное**:

- **Адрес кейса (UID)**: только окончание адреса, например `yota`, без `/projects/`. Используйте латиницу, цифры и дефисы. После запуска не меняйте UID без настройки перенаправления со старого URL.
- **Заголовок H1**: например «Yota: bullet time через 3D-скан всей съёмочной сцены».
- **Краткое описание**, **обложка**, **клиент**, **агентство**, **год**, **формат**, **срок**.
- **Категория** нужна для автоматического блока «Другие кейсы». Это не переименовывает фильтры существующей ленты.
- **Направления**: добавьте нужные теги.
- **Задача**, **решение**, **результат**: форматированный текст, списки и ссылки.

Вкладка **Видео и кадры**:

- Добавьте ролики. Первый будет главным, следующие появятся ниже. Нужна прямая ссылка на файл `.mp4` или `.webm`, например с `videos.twin3d.ru`, а не адрес страницы YouTube/VK.
- Укажите постер, название и описание каждого видео.
- Для разметки `VideoObject` заполните настоящую **дату публикации видео**, постер и описание. Дата создания документа не подставляется вместо неё. Длительность указывается в секундах.
- Добавьте кадры и подписи. Заполняйте Alt у изображений. Если видео нет, сверху показывается обложка.

Вкладка **SEO**:

- **Title**, **Description**, **превью 1200 × 630**. Если Title не заполнен, используется H1 + Twin3D; для Description есть резерв из краткого описания/задачи. Перед запуском лучше заполнить оба поля явно.
- **Скрыть от поисковиков** по умолчанию выключено. Если включить, страница получит `noindex` и не попадёт в sitemap. Для незаконченного кейса лучше оставить документ черновиком.
- Canonical создаётся автоматически на адрес самого кейса. Вручную вводить его не нужно.

Вкладка **Ссылки**:

- **Behance**: необязательная ссылка на полную версию.
- **Ссылка кнопки «Хочу похожий проект»**: необязательна. По умолчанию открывается Telegram `D_Twin3D` с текстом о выбранном кейсе. Пользователь сам отправляет сообщение. Для иной веб-формы в URL добавляется параметр `project=slug`; сама форма должна уметь читать этот параметр.

Пустые необязательные блоки не выводятся. Не оставляйте в публикуемом тексте `[агентство]`, `[год]` и другие заглушки из ТЗ. Неподтверждённые цифры и фразы убирайте.

## Как связать страницу с карточкой

1. Опубликуйте заполненный документ **Кейс**.
2. Откройте существующий документ **Projects**, слайс **CaseFilters**, нужную карточку.
3. В новом поле **Страница кейса** выберите опубликованный документ.
4. Сохраните и опубликуйте изменение Projects.

Для десяти проектов из ТЗ внутренние страницы подбираются автоматически по существующим карточкам и UID из таблицы ниже. Явное поле **Страница кейса** имеет приоритет и пригодится для переименованных/новых карточек. До публикации соответствующего документа кнопка целевого кейса скрыта, чтобы не отправлять посетителя на 404 или Behance. У остальных проектов старые внешние ссылки сохраняются. Внутри кейса используется поле **Behance**; если оно пустое, берётся прежняя Behance-ссылка соответствующей карточки. Несколько карточек фильмов могут ссылаться на один документ `kino`.

Важно: публикация Prismic может запускать уже существующий у вас webhook деплоя. Пока код шаблона не загружен на сервер, новые страницы будут доступны только локально. Согласуйте публикацию контента с загрузкой кода.

## Перед публикацией кода

Выполните `npx next typegen`, `npx tsc --noEmit`, `npm run test:cases` (Node 22.18+ или 24) и `npm run build`. Дождитесь завершения сборки. Не запускайте build одновременно с dev в одной папке: оба используют `.next`.

Для каждого заполненного кейса проверьте прямой URL и обновление страницы, кнопку закрытия, Escape, «Назад», мобильную ширину, видео и ссылки. В исходном HTML должны быть H1 и текст, индивидуальные метаданные и canonical. `/sitemap.xml` содержит только опубликованные документы с UID и заголовком, без `noindex`. `/robots.txt` разрешает обход сайта. Новые кейсы читаются без постоянного кэша, поэтому отдельная пересборка для каждого кейса этому шаблону не нужна.

После выкладки на сервер проверьте реальные URL и добавьте sitemap в Яндекс Вебмастер. Затем отправьте кейсы на переобход. Попадание в поиск и позиции не гарантируются самим шаблоном.

## Границы этой доработки

Готовы модель кейса, SSR-шаблон с оверлеем, связь с рабочим слайсом, метаданные, VideoObject, sitemap и robots. Объединение дублей, приоритеты в категориях, переписывание всей ленты, цели Метрики и правки подвала относятся к следующим пунктам полного ТЗ. Сами 10 документов заполняются в Prismic вручную.

Изменения не закоммичены и не отправлены на GitHub. Для отката проверяйте список файлов в Git и отменяйте только изменения этой доработки; не используйте массовый сброс, если успели внести собственные правки.
